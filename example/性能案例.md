# AspectD 性能排查实战案例

## 核心思路

**AspectD 粗筛（找到哪个方法慢）→ DevTools 细查（看方法内部瓶颈）**

---

## 1. 通配符自动发现慢方法

```dart
@Call("package:app/services/.*", ".*", "-.*", isRegex: true)
dynamic hookAllMethods(PointCut pointcut) {
  if (_isProcessing) return pointcut.proceed();
  _isProcessing = true;
  try {
    final sw = Stopwatch()..start();
    final result = pointcut.proceed();
    sw.stop();
    final cost = sw.elapsedMicroseconds;
    if (cost >= 500) {
      print('⚠️ ${pointcut.target.runtimeType}.${pointcut.function} 耗时: ${cost}μs');
    }
    return result;
  } finally {
    _isProcessing = false;
  }
}
```

### isRegex 参数说明

| 参数 | 示例 | 含义 |
|------|------|------|
| importUri | `"package:app/services/.*"` | 匹配目录下所有文件 |
| clsName | `".*"` | 匹配所有类 |
| methodName | `"-.*"` | 匹配所有实例方法 |
| methodName | `"+.*"` | 匹配所有静态/工厂方法 |

### 注意事项

- importUri 不要用 `"package:app/.*"` 全包匹配，会匹配到 Widget.build()、日志类等，导致递归或影响渲染
- 精确到业务目录，如 `"package:app/services/.*"`
- 加重入保护 `static bool _isProcessing` 防止递归
- 异步方法 + isRegex @Call 存在 transformer bug，暂不支持

## 2. 按场景匹配

### 数据库慢查询

```dart
@Call("package:app/dao/.*", ".*", "-.*", isRegex: true)
```

发现问题：某个查询扫全表、未命中索引

### JSON 解析卡顿

```dart
@Call("package:app/models/.*", ".*", "+fromJson", isRegex: true)
```

发现问题：大列表一次性解析（应分片 / compute()）

### 图片处理阻塞

```dart
@Call("package:app/image/.*", "ImageProcessor", "-.*", isRegex: true)
```

发现问题：主线程压缩大图（应移到 Isolate）

### 页面初始化慢

```dart
@Execute("package:app/pages/.*", ".*", "-initState", isRegex: true)
```

发现问题：initState 里做了同步 IO 或大量计算

## 3. 线上 APM 监控

```dart
@Call("package:app/services/.*", ".*", "-.*", isRegex: true)
dynamic hookAllMethods(PointCut pointcut) {
  if (_isProcessing) return pointcut.proceed();
  _isProcessing = true;
  try {
    final sw = Stopwatch()..start();
    final result = pointcut.proceed();
    sw.stop();
    // 只上报超过阈值的慢方法，减少噪音
    if (sw.elapsedMilliseconds > 100) {
      ApmReporter.report(
        method: '${pointcut.target.runtimeType}.${pointcut.function}',
        duration: sw.elapsedMilliseconds,
      );
    }
    return result;
  } finally {
    _isProcessing = false;
  }
}
```

## 4. 排查流程

```
Step 1: 复现卡顿场景
        ↓
Step 2: AspectD regex hook 全量插桩业务层
        输出: ⚠️ DatabaseHelper.queryUsers 耗时: 45ms
        ↓
Step 3: 锁定慢方法，用 DevTools CPU Profiler 下钻
        看方法内部哪一行最耗时
        ↓
Step 4: 优化
        - 耗时计算 → Isolate / compute()
        - 大 JSON → 分片解析
        - 频繁 build → const / 缓存
        ↓
Step 5: 保留 hook，持续监控是否回归
```

---

## 5. 阈值参考

| 场景 | 阈值 | 影响 |
|------|------|------|
| 任意同步方法 | > 16ms | 掉 1 帧 |
| 网络请求 | > 3000ms | 用户感知慢 |
| 数据库操作 | > 100ms | 页面加载慢 |
| JSON 解析 | > 50ms | 列表滑动卡 |
| 图片处理 | > 33ms | 掉 2 帧 |

---

## 6. AspectD vs 其他方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| DevTools | 精确到行、火焰图 | 只能开发环境、手动操作 |
| 手动埋点 | 灵活 | 侵入代码、容易遗漏 |
| **AspectD regex** | **零侵入、全量覆盖、可线上** | 只能到方法级、async 有限制 |

---

## 7. 已知限制

- `isRegex: true` + `@Call` 匹配到 async 方法时 transformer 崩溃（Null cast to Procedure）
- 解决：异步方法单独文件，或用精确 `@Call`（不用 regex）单独 hook
- 同步方法完全正常，实际排查主线程卡顿已够用
